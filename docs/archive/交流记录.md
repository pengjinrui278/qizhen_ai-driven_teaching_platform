我对文档核心内容的理解如下：

- MathMirror 不是普通的数学问答或解题 AI，而是一个持续理解学生学习过程的个性化教学智能体平台。
- 核心架构由三类对象组成：
  - `Student Mirror`：长期认识学生，维护个人学习证据、知识状态和动态学习假设。
  - `Course Mirror`：真正处理课程专业问题，维护课程知识、题目结构、提示体系、验证工具和课程经验。
  - `Assignment Workspace`：聚合某班某次作业周期内的过程与作品证据，生成教师报告，任务结束后清理临时上下文。
- 三者的关键边界是：
  - Course Mirror 保存“课程是什么、题目怎样处理”；
  - Student Mirror 保存“这个学生和知识之间是什么关系”；
  - Workspace 保存“这个班在这个阶段发生了什么”。
- 产品的核心数据不是最终答案，而是学生在得到答案之前的过程：在哪里卡住、需要什么提示、提示后能否继续、是否反复出现相同困难。
- 学生建模采用“假设—证据—更新”，而不是依据单次行为给学生分类、打分或贴标签。
- 个性化必须真正改变后续帮助。例如，同一道题可以根据不同学生的历史困难提供不同层级和类型的提示，而不只是改变称呼或文案。
- 默认交互强调低摩擦：学生上传题目后可以直接点击“我卡住了”，获得尽量小而有效的渐进式提示；不强迫填写诊断问卷，也不采用令人疲惫的连续反问。
- 教师端的目标不是展示更多统计数据，而是输出“本周最值得教学关注的现象”，帮助教师决定下一次习题课、答疑或教学设计应如何调整。
- 数据采用双通道：
  - 学生求助轨迹覆盖有限，但过程深；
  - 作业和 TA 批改接近全班覆盖，但只能看到最终作品；
  - 小测和考试作为较独立的校准证据。
- TA 的角色是人类校准器：AI 提出候选问题、聚合模式，TA 确认数学判断；系统不试图替代教师或助教。
- 每个 Course Mirror 都应包含课程资料、结构化知识、题目—解法图、提示阶梯、课程专用 Harness、Eval Set 和学习证据输出，不能只是更换 Prompt 或给教材做简单 RAG。
- 比赛阶段采取“1 门深做 + 4 门真实可用”的策略：
  - 数学分析承担完整闭环验证；
  - 高代、大物、点拓、常微分承担跨课程扩展性验证。
- 五门课程共用 Student Mirror 和统一的 Learning Evidence Schema，但每门课程拥有自己的知识层、Harness 和 Eval。
- 隐私原则非常明确：不默认向教师暴露私人对话，不把求助或查看答案作为惩罚指标；身份化 Student Mirror 在学生离校后按政策导出、缓冲并删除，只有去身份化、聚合且经人工审核的课程经验可以长期进入 Course Mirror。
- 第一阶段真正要验证的是：学生是否愿意使用、自然求助能否产生有价值的过程证据、长期证据能否形成可解释且可修正的个性化观察，以及这些信息能否转化为教师可行动的教学洞察。

整份文档最稳定的产品原则可以概括为：

> 先帮助学生，再观察学生；先保存证据，再形成假设；个性化必须改变下一次帮助，教学分析必须能够影响下一次教学。

## 一、总体技术架构

```text
学生端 / 教师端 / TA端 / 管理端
              │
              ▼
      Next.js Web Application
              │
              ▼
       FastAPI Backend API
              │
    ┌─────────┼────────────┐
    ▼         ▼            ▼
Student    Course       Assignment
Mirror     Mirror       Workspace
    │         │            │
    └──────┬──┴──────┬─────┘
           ▼         ▼
     Evidence Engine │
           │         │
           ▼         ▼
   Hypothesis Engine Teacher Insight
           │
           ▼
   Student Model / 个性化决策

基础设施：
PostgreSQL + pgvector
Redis + 异步任务队列
S3/MinIO 对象存储
LLM / Embedding / OCR / 数学工具
日志、Tracing、Eval
```

最关键的架构原则是：

> Student Mirror、Course Mirror 和 Assignment Workspace 在代码、数据表和权限上明确分离，但第一阶段部署在同一个后端应用中。

这样避免“逻辑没有分清，却先拆成十几个服务”的问题。

### 3. AI 编排层

不建议把整个系统绑定在某个 Agent 框架上。

建议自己定义稳定接口：

```python
class CourseMirror:
    async def identify_problem(...)
    async def retrieve_context(...)
    async def generate_hint(...)
    async def review_solution(...)
    async def extract_evidence(...)
    async def run_harness(...)
```

内部可以使用：

- 简单步骤：普通 Python service；
- 多步骤、可重试的答疑流程：LangGraph；
- 模型访问：自建 `ModelGateway`；
- 结构化输出：Pydantic Schema；
- 长流程持久化：数据库 checkpoint。

LangGraph 可以用于有状态、多步骤和可恢复流程，但只作为实现细节。其官方持久化机制区分了线程内 checkpoint 与跨线程 store，这与“当前对话状态”和“长期 Student Model”的分离比较契合。[LangGraph 持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)

模型层应设计成可替换：

```text
ModelGateway
  ├─ chat()
  ├─ structured_output()
  ├─ embedding()
  ├─ vision_ocr()
  └─ moderation()
```

业务代码不得直接散落调用具体模型厂商。

### 4. 数据存储

第一阶段用一个 PostgreSQL 作为主数据库：

- 关系数据；
- JSONB 结构化证据；
- 全文检索；
- 向量检索；
- 权限与审计数据。

向量检索使用 pgvector，不单独引入 Milvus、Weaviate 或 Elasticsearch。pgvector 能同时支持精确/近似向量检索，并可和 PostgreSQL 全文检索组合成混合检索，足以支撑当前课程规模。[pgvector 官方项目](https://github.com/pgvector/pgvector)

其他存储：

| 数据 | 存储 |
|---|---|
| 教材 PDF、题目图片、学生作业 | S3 或 MinIO |
| 缓存、速率限制、任务队列 | Redis |
| 原始日志与追踪 | OpenTelemetry 后端 |
| 临时上传文件 | 对象存储临时区 |
| CoursePack 版本产物 | 对象存储 + PostgreSQL 元数据 |

暂时不要引入图数据库。知识图谱先用普通关系表表达：

```text
knowledge_nodes
knowledge_edges
problems
problem_knowledge_links
solution_paths
solution_steps
hint_nodes
```

如果未来出现大规模复杂图查询，再评估 Neo4j。

### 5. 数学与课程 Harness

统一 Harness 接口：

```python
class HarnessResult(BaseModel):
    status: Literal["passed", "failed", "uncertain"]
    checks: list[CheckResult]
    corrected_output: str | None
    warnings: list[str]
```

各课程挂载不同工具：

- 数学分析：定理条件检查、证明步骤检查、数值反例抽样；
- 高等代数：SymPy 矩阵与符号计算；
- 大学物理：Pint 单位与量纲检查；
- 点集拓扑：定义、量词、反例库和逻辑规则；
- 常微分方程：SymPy、SciPy 数值求解与残差验证。

Harness 不能直接决定“答案一定正确”，只能输出：

- 通过了哪些检查；
- 哪些地方失败；
- 哪些地方无法验证；
- 是否需要模型重试或人工确认。

## 五、核心调用链

### 学生求助

```text
1. 学生上传题目或输入问题
2. Student Mirror 识别课程、任务和学生
3. Context Selector 读取最小个人上下文
4. 调用相应 Course Mirror
5. Course Mirror 做题目识别和混合检索
6. 规划当前提示层级
7. Harness 检查课程事实、条件与关键推理
8. 流式返回提示
9. Evidence Extractor 生成结构化证据
10. Student Mirror 更新个人状态和学习假设
11. 若属于当前作业，同时写入 Workspace
```

注意第 9～11 步应通过异步任务完成，不能让学生一直等待。

### 教师/TA 工作流

```text
学生作业
  ↓
OCR / 版面识别
  ↓
AI 生成候选问题
  ↓
TA 确认、否定或修改
  ↓
形成可靠作品证据
  ↓
与 Workspace 中的过程证据聚合
  ↓
生成班级学习现象
  ↓
教师确认或修改教学建议
```

## 七、开发顺序

### 阶段 0：先冻结协议与评价标准

先完成：

- 三类对象的数据边界；
- Course Mirror Request/Response；
- Learning Evidence Schema；
- Harness Result Schema；
- 隐私可见范围；
- 数分首批 Eval Set；
- 核心用户流程原型。

这是第一优先级。没有稳定协议，后面五门课程会各自长成不同系统。

### 阶段 1：打通“数分单题求助”纵向切片

只做一条完整链路：

```text
登录 → 选择数分 → 上传题目
→ 题目识别 → 检索 → 第一层提示
→ 再提示 → 完整思路 → 记录事件
```

此时暂不做复杂学生画像和教师看板。

完成标准：

- 引用课程资料；
- 回答可以流式展示；
- 提示层级可追踪；
- 每次交互都有结构化事件；
- 有 30～50 道人工核验题作为回归测试。

### 阶段 2：建设数分 CoursePack 与 Harness

开发：

- 教材解析与版本管理；
- 定义/定理/题目索引；
- 题目—解法—提示结构；
- 混合检索；
- 定理条件检查；
- 完整答案泄露检查；
- 数分 Eval 流水线。

这一阶段目标不是“录入整本教材”，而是把一个有代表性的章节做深。

### 阶段 3：Evidence Engine

将聊天行为转换为结构化证据：

- 首次求助；
- 提示类型；
- 继续请求；
- 完整答案请求；
- 学生声明完成；
- 后续相似题自然复测；
- 证据来源和强度。

必须保留原始事件引用，保证每条判断可追溯。

### 阶段 4：Student Mirror 和 Hypothesis Engine

第一版不要上复杂知识追踪模型。先采用：

```text
明确规则
+ 时间衰减
+ 支持/反对证据计数
+ 人工可解释的离散置信等级
```

先实现：

- 学习证据时间线；
- 知识关系状态；
- 动态学习假设；
- 支持与相反证据；
- “为什么这么说”页面；
- 假设弱化和撤销。

### 阶段 5：个性化闭环

让 Student Model 真正改变提示：

```text
统一提示组
vs
基于历史证据的个性化提示组
```

记录：

- 使用了哪些个人证据；
- 为什么改变提示；
- 学生是否继续请求；
- 后续是否能独立完成；
- 个性化是否优于统一提示。

做到这里，MathMirror 学生端的核心命题才真正成立。

### 阶段 6：Assignment Workspace 与 TA Copilot

开发：

- 创建班级和作业；
- 关联题目；
- 导入作业图片/PDF；
- AI 预分析；
- TA 确认/否定；
- 同类问题聚合；
- 覆盖率与数据限制；
- 作业截止后的教师报告；
- Workspace 到期清理。

报告必须区分：

- 全班作业证据；
- MathMirror 主动用户过程证据；
- TA 确认证据；
- 系统推断。

### 阶段 7：四门扩展 Course Mirror

不要同时独立建设四套后端。复用统一接口，分别补充：

- CoursePack；
- 代表性题目；
- 一种特色 Harness；
- Eval Set；
- Learning Evidence 映射。

推荐顺序：

1. 高代：最容易复用数学结构和 SymPy；
2. 常微分：可展示符号与数值校验；
3. 大物：增加单位、量纲和模型检查；
4. 点拓：检验抽象定义、量词和反例能力。

每门课程先覆盖一个代表性章节，保证真实可用，再扩展范围。

### 阶段 8：治理、实验和比赛打磨

最后完成：

- 学生数据授权；
- 教师可见范围；
- 对话导出与删除；
- Workspace 自动清理；
- 审计日志；
- 模型调用成本监控；
- Prompt、CoursePack、Harness 和 Eval 版本绑定；
- 真实学生实验；
- 个性化与统一提示对照；
- TA 确认率和教师采纳率统计。

## 八、推荐的比赛版最小范围

比赛版不要把所有页面都做满。建议只保证以下闭环完整：

```text
学生上传数分题
→ 获得渐进提示
→ 产生 Learning Evidence
→ 多次交互形成可解释学习假设
→ 下一次提示因学生历史发生变化
→ 作业进入 TA 确认流程
→ 教师获得一份可行动的班级报告
```

另外四门课分别展示：

```text
课程资料检索
+ 课程风格回答
+ 一种专用 Harness
+ 统一 Evidence 输出
```

## 九、必须避免的技术误区

- 一开始拆十几个微服务；
- 每门 Course Mirror 部署一套完全独立系统；
- 直接把完整聊天记录当 Student Model；
- 用向量数据库代替结构化课程知识；
- 让大模型自由生成无法追溯的学生画像；
- 不记录提示决策过程，却声称已经个性化；
- 在没有 Eval 前进行微调；
- 把图数据库、知识图谱或 Agent 框架当作产品核心；
- 把未经 TA 确认的 AI 作业判断当作事实；
- 为方便开发而混合身份化学生数据与课程长期资产。

如果团队规模有限，开发资源应优先分配为：

```text
数分答疑与 Harness       30%
Evidence 与 Student Model 25%
学生端体验               20%
Workspace 与 TA 端       15%
四门扩展课               10%
```

核心判断只有一个：先做出一条“当前帮助 → 留下证据 → 更新理解 → 改变下次帮助”的纵向闭环，再扩课程和页面。

> 如果我们想把这个平台最终接到学在浙大平台中按照现有技术栈会不会有不兼容的问题，或者我们可以爬取学在浙大中的数据来做这个平台，最后做成一个手机app和网页都有的教学平台。然后如何把学生的拍题或者是教材中的定理习题等做成模型可训练的数据格式。然后我们的名字不要用MathMirror，不只有数学课程，其他课程也可以加入进来。

## 一、会不会与“学在浙大”不兼容

从公开资料看，“学在浙大 2.0”已经与教务系统、浙大钉、智云课堂等系统进行统一身份、统一数据和统一服务层面的贯通，并拥有 Web 和移动端能力。[浙江大学信息技术中心介绍](https://its.zju.edu.cn/2026/0806/c49384a3193637/page.htm)

但公开资料没有给出可供第三方直接开发的完整 API、Webhook、LTI 或 OAuth 接入文档。因此目前只能确定：

- 平台具备系统集成能力；
- 不能确定是否向学生项目开放；
- 不能确定是否支持 LTI 1.3；
- 不能确定第三方能读取哪些课程、作业、成绩和用户数据；
- 不能确定 AI 服务能否部署在校外云环境。

所以不要为了“猜测学在浙大的后端技术栈”调整产品，而应增加一个专门的集成层。

```text
你们的平台核心业务
          │
          ▼
Integration Gateway
  ├─ ZJU Identity Adapter
  ├─ LMS Course Adapter
  ├─ Enrollment Adapter
  ├─ Assignment Adapter
  ├─ Submission Adapter
  ├─ Grade Adapter
  ├─ Content Adapter
  └─ Event/Webhook Adapter
          │
          ▼
学在浙大 / 教务系统 / 浙大钉
```

核心系统只认识自己的标准数据模型，不直接依赖“学在浙大”的字段名称。

例如：

```python
class ExternalCourse:
    external_platform: str
    external_course_id: str
    title: str
    term: str
    teacher_ids: list[str]

class ExternalAssignment:
    external_assignment_id: str
    course_id: str
    title: str
    due_at: datetime | None
    problem_refs: list[str]
```

以后即使接入 Moodle、Canvas、雨课堂或其他学校平台，也只需更换 Adapter。

## 二、建议争取的接入方式

优先级从高到低如下。

### 方案 A：LTI 1.3

如果“学在浙大”支持 LTI，这是最理想的方式。LTI 1.3 专门用于把外部教学工具安全地接入 LMS，并可以配合：

- 统一启动与身份传递；
- 课程和角色同步；
- 作业与成绩服务；
- 教师选择外部学习内容；
- 从 LMS 直接进入某个课程智能体。

LTI 1.3 使用 OIDC 和 OAuth 2.0 安全模型；LTI Advantage 还定义了成员角色、作业成绩和内容嵌入等服务。[1EdTech LTI 1.3 实施指南](https://standards.1edtech.org/lti/guides/implementation_guide/implementation-guide)

但目前不能假定“学在浙大”支持它，必须向信息技术中心确认。

### 方案 B：校方 SSO + 官方 API

如果不支持 LTI，可以采用：

```text
学校统一身份认证
+
课程/选课 API
+
作业和提交 API
+
课程资料 API
+
事件回调或定时增量同步
```

推荐的数据流是：

```text
学在浙大负责：
课程组织、选课、作业发布、成绩和正式教学记录

新平台负责：
AI答疑、渐进提示、过程证据、个人学习状态、课程智能体

必要结果回写：
教师报告、作业辅助分析、经过教师确认的教学洞察
```

不要重复建设选课、成绩和作业发布系统。

### 方案 C：教师授权导入

比赛和试点阶段如果尚未获得系统 API，可采用：

- 教师导出的课程学生名单；
- 教师授权上传的教学大纲和课件；
- 作业题目和脱敏后的学生作品；
- CSV、Excel、ZIP、PDF 批量导入；
- 学生主动上传自己的题目与作业。

这比爬虫可靠，也更容易控制数据范围。

## 三、是否可以爬取“学在浙大”

技术上可能抓到页面，不代表应该抓。

尤其不要做：

- 保存学生账号和密码；
- 复用学生 Cookie 批量访问；
- 绕过验证码或访问控制；
- 抓取未授权的学生名单、成绩和提交内容；
- 把抓到的数据直接发送给外部模型；
- 把不同课程的数据混入长期训练集。

教学记录、作业、成绩、身份信息和学习轨迹通常涉及个人信息；数据处理需要明确目的、种类、保存期限、接收方和删除方式，并采取访问控制、加密、审计等措施。《网络数据安全管理条例》也明确要求网络数据处理者建立制度并采取加密、备份、访问控制和安全认证等措施。[国家行政法规库](https://xzfg.moj.gov.cn/front/law/detail?LawID=1734&Query=)

安全路线是：

```text
公开网页资料
→ 遵守站点规则和版权要求

学生自己的数据
→ 学生主动导出/上传 + 明确告知和授权

教师课程资料
→ 教师或学校授权

全班作业、成绩、教学轨迹
→ 学校正式授权接口或受控数据导出
```

如果校方允许“采集器”作为临时接入方式，也应该取得书面授权，限定课程、账号、字段、频率、用途和删除期限，而不是自行部署爬虫。

## 四、为接入校方平台需要调整的技术骨架

原技术栈可以保留，但应增加五层能力。

### 1. 身份映射层

```text
本平台 user_id
  ↔ 学校统一身份 ID
  ↔ LMS user_id
  ↔ 学号/工号的受控映射
```

业务表尽量不直接使用学号作为主键。

### 2. 数据来源与授权记录

所有外部数据都要带：

```text
source_system
external_id
authorization_scope
authorized_by
ingested_at
retention_policy
expires_at
content_license
```

### 3. 同步状态

```text
integration_connections
sync_jobs
sync_cursors
sync_failures
external_object_mappings
webhook_events
```

同步必须幂等，同一份作业被推送两次不能产生两份记录。

### 4. 数据分区

至少逻辑隔离：

```text
tenant/school
course
class
student
workspace
```

所有查询都必须经过作用域过滤，防止一门课访问另一门课的数据。

### 5. 模型调用网关

模型调用前统一执行：

```text
权限检查
→ 数据最小化
→ 敏感字段去除/替换
→ 模型供应商策略检查
→ 调用
→ 输出安全检查
→ 审计
```

学校可能要求模型和数据库校内化部署。因此 `ModelGateway` 必须支持：

- 公有云模型；
- 学校已有模型服务；
- 校内私有部署模型；
- 不同数据等级使用不同模型。

## 五、网页和手机 App 怎么做

建议采用 API-first：

```text
                 ┌─ Next.js Web / PWA
                 │
FastAPI API ─────┼─ React Native / Expo App
                 │
                 └─ 学在浙大内嵌入口 / LTI Tool
```

### 第一阶段：响应式 Web + PWA

先做好：

- 手机浏览器拍照上传；
- 流式问答；
- 数学公式显示；
- 题目图片标注；
- 学习状态；
- 教师和 TA 页面。

PWA 可以添加到手机桌面，足以支撑首轮试点。

### 第二阶段：React Native/Expo App

选择 React Native 的原因是可以与 Next.js 共享：

- TypeScript 数据类型；
- Zod Schema；
- OpenAPI SDK；
- 认证逻辑；
- 埋点协议；
- 部分无 UI 业务逻辑。

不建议强行让 Web 和 App 共享所有 UI 组件。拍摄、裁剪、通知、离线缓存等功能应该使用原生移动端交互。

App 特别适合做：

- 相机拍题；
- 多页作业扫描；
- 图片裁剪和透视校正；
- 消息提醒；
- 语音提问；
- 离线保存草稿；
- 快速进入最近课程。

## 六、产品应从“数学平台”改成什么

产品定位可以改为：

> 面向大学课程的跨学科个性化学习智能体平台。

原来的三个技术对象也应去数学化：

| 旧称 | 建议通用称呼 | 职责 |
|---|---|---|
| Student Mirror | Student Agent / Learner Model | 长期理解学生 |
| Course Mirror | Course Agent | 负责课程专业能力 |
| Assignment Workspace | Learning Workspace | 某班某教学任务的临时上下文 |
| MathMirror Kernel | Learning Intelligence Kernel | 路由、证据、身份、策略 |

课程可以逐步扩展为：

```text
Course Agent
  ├─ 数学分析
  ├─ 高等代数
  ├─ 大学物理
  ├─ 大学化学
  ├─ 程序设计
  ├─ 经济学
  ├─ 历史
  ├─ 法学
  └─ 外语
```

但不同学科不能只是换 Prompt。例如：

- 编程课需要代码沙箱和测试用例；
- 化学需要结构式、反应条件和实验安全检查；
- 语言课需要语音、写作批改和词汇记忆；
- 历史课需要来源引用和论证结构；
- 法学需要法条版本、案例与管辖范围；
- 工程课需要仿真、单位和安全边界。

### 名称候选

可以先用一个内部代号，暂不急着定正式品牌：

- 知镜 EduLens
- 学脉 LearnPulse
- 知伴
- 学迹
- 启知
- CourseWeave
- LearnWeave

我相对更推荐“知镜 EduLens”或“学脉 LearnPulse”：

- “知镜”保留“帮助学生认识自己的学习”这一核心；
- “学脉”强调持续学习轨迹和课程之间的连接；
- 都不限定数学。

正式使用前仍需检查商标、域名、应用商店重名和学校品牌使用规范。

## 七、拍题数据如何转换

原始图片不能直接等同于训练数据。建议形成以下流水线：

```text
学生拍照
  ↓
图像质量检测
  ↓
裁剪 / 旋转 / 透视校正 / 去阴影
  ↓
版面分析
  ├─ 题目正文
  ├─ 公式
  ├─ 图表
  ├─ 学生手写过程
  └─ 批改痕迹
  ↓
OCR + 数学公式识别
  ↓
人工或模型校对
  ↓
题目去重与标准化
  ↓
关联课程、章节、知识点
  ↓
权限和身份检查
  ↓
进入 CoursePack / Eval / 训练候选池
```

图片保存在对象存储中，JSONL 只保存引用：

```json
{
  "record_id": "capture_001",
  "image_uri": "s3://dataset/raw/capture_001.jpg",
  "owner_scope": "student_private",
  "course_id": "analysis_1",
  "content_type": "problem_with_work",
  "ocr": {
    "problem_text": "设函数……证明……",
    "latex_blocks": ["\\lim_{n\\to\\infty} a_n"],
    "student_work": "由……可得……"
  },
  "regions": [
    {
      "type": "problem",
      "bbox": [80, 110, 920, 640]
    },
    {
      "type": "student_solution",
      "bbox": [70, 680, 930, 1710]
    }
  ],
  "quality": {
    "ocr_verified": true,
    "formula_verified": true
  },
  "rights": {
    "allowed_for_rag": true,
    "allowed_for_eval": false,
    "allowed_for_training": false
  }
}
```

这里要把三种权利分开：

- 可用于当前答疑；
- 可进入课程知识库；
- 可进入评测集；
- 可用于模型训练。

学生上传一张图片用于答疑，不自动意味着允许拿去训练。

## 八、教材、定理和习题的数据格式

建议建立通用的 `CoursePack`，而不是每门课随意组织文件。

### 定义和定理

```json
{

  "type": "theorem",
  "course_id": "mathematical_analysis_1",
  "title": "Rolle定理",
  "statement": "若函数满足……则存在……",
  "statement_latex": "...",
  "conditions": [

    "在开区间(a,b)内可导",
    "f(a)=f(b)"
  ],
  "conclusion": "存在ξ∈(a,b)，使f'(ξ)=0",
  "prerequisites": [
    "continuous_function",
    "derivative"
  ],
  "common_misuses": [
    "未验证闭区间连续",
    "遗漏端点函数值相等"
  ],
  "source": {
    "document_id": "textbook_001",
    "page": 126,
    "edition": "authorized-edition"
  },
  "rights": {
    "use_scope": "licensed_course_rag",
    "trainable": false
  }
```

## 九、哪些数据适合训练模型

不要把所有数据都做成同一种 SFT 数据。

### 1. 知识检索数据

用于 RAG，不一定用于训练：

```json
{
  "id": "chunk_001",
  "text": "Rolle定理的条件包括……",
  "metadata": {
    "course_id": "analysis_1",
    "knowledge_id": "theorem_rolle",
    "source_page": 126,
    "license": "course_internal"
  }
}
```

### 2. 教学对话 SFT

训练“怎样给提示”，而不是训练教材事实：

```json
{
  "messages": [
    {
      "role": "system",
      "content": "你是课程学习助手。优先给最小有效提示。"
    },
    {
      "role": "user",
      "content": "这道题我不知道怎么开始。"
    },
    {
      "role": "assistant",
      "content": "先不要寻找具体公式。观察结论是否可以转化为某个函数在区间内导数为零。"
    }
  ],
  "metadata": {
    "course_id": "analysis_1",
    "interaction_mode": "first_hint",
    "hint_level": 1,
    "human_verified": true
  }
}
```

### 3. 证据抽取训练数据

```json
{
  "input": {
    "problem_context": "……",
    "conversation": [
      "学生：这里为什么可以使用Rolle定理？",
      "助手：先检查定理条件……"
    ]
  },
  "output": {
    "event_type": "condition_help_request",
    "related_theorem": "theorem_rolle",
    "reasoning_stage": "theorem_applicability",
    "evidence_strength": "weak",
    "observation": "本次交互显示学生对定理适用条件请求了帮助"
  }
}
```

注意输出只能描述本次观察，不能直接写“学生定理理解能力差”。

### 4. 偏好数据

用于训练“哪一种提示更合适”：

```json
{
  "prompt": "学生已经能识别Rolle定理，但过去常在构造辅助函数时卡住。",
  "chosen": "如果要让Rolle定理可用，你希望新函数在两个端点满足什么关系？",
  "rejected": "Rolle定理的内容是：若函数在闭区间上连续……",
  "reason": "避免重复学生已掌握的内容，把支架放在实际困难位置。"
}
```

### 5. Eval 数据

Eval 必须与训练集分开：

```json
{
  "case_id": "eval_hint_001",
  "input": {},
  "expected": {
    "must_check": [
      "不直接泄露完整答案",
      "提示与学生历史相关",
      "定理条件正确"
    ]
  },
  "rubric": {},
  "split": "held_out_test"
}
```

## 十、教材版权和训练策略

建议采用明确原则：

```text
有授权的教材内容
→ 可按授权范围用于课程内检索

公开且许可兼容的材料
→ 可按许可证用于检索或训练

教师自建材料
→ 教师/学校明确授权

学生作业和对话
→ 单独告知、去身份化、筛选并审核

来源或版权不明确
→ 不进入训练集
```

尤其不要因为能 OCR 出教材，就默认拥有模型训练权。

在技术上，为每条数据增加：

```text
copyright_owner
license_type
allowed_for_runtime
allowed_for_rag
allowed_for_eval
allowed_for_training
allowed_model_scope
retention_until
```

数据构建系统在导出训练集时自动过滤，而不是靠开发者记忆。

## 通用 Course Model 的实现方向

当前统一模型为：

```text
CourseProfile
├─ SourceDocument
├─ KnowledgeNode / KnowledgeEdge
├─ Problem
├─ SolutionPath / SolutionStep
├─ HintNode
├─ CommonMistake
├─ HarnessSpec / HarnessResult
├─ LearningEvidence
└─ EvalCase
```

课程细化不修改 Student Mirror，而是通过 Course Profile 和插件能力完成：

```text
通用 Course Mirror 协议
        │
        ├─ 数分：定理条件、量词、证明逻辑
        ├─ 高代：符号计算、秩与维数条件
        ├─ 大物：量纲、模型假设、数量级
        ├─ 点拓：定义约定、量词、反例
        └─ 常微分：方程分类、残差、存在唯一性
```

这保证五门课程不是五套互不兼容的系统，也不是简单更换 Prompt。

## 一、准确区分四个东西

```text
通用基础模型
    │
    ├─ 通用教学行为能力
    │
    ├─ CoursePack 课程知识
    │
    ├─ 课程专用工具与 Harness
    │
    └─ Course Profile
           ↓
      某门 Course Mirror
```

### 通用基础模型

负责语言、推理、图像理解、基础学科知识。

通常不从零训练，而是选择一个已有强模型。

### 通用教学模型

负责共同教学行为：

- 不立即泄露答案；
- 生成渐进提示；
- 判断学生请求的是方向、条件还是局部推进；
- 从交互中抽取 Learning Evidence；
- 表达不确定性；
- 根据学生历史改变帮助。

这一层可以由五门课程的高质量教学数据共同训练。

### CoursePack

保存课程真实知识：

- 教材版本；
- 定义、定理、公式；
- 章节顺序；
- 题目；
- 解法路径；
- Hint Ladder；
- 常见错误；
- 教师课程材料。

它主要通过 RAG 和结构化检索提供知识，不应该主要靠模型参数死记。

### Course Mirror

不是单独一个神秘模型，而是一套组合：

```text
基础模型
+ 通用教学策略
+ 某课程 CoursePack
+ 某课程 Prompt/Profile
+ 某课程工具和 Harness
+ 某课程 Eval
+ 可选的课程微调参数
```

## 二、应该怎样训练“通用模型”

我们不建议从零预训练大模型，成本过高，也没有必要。

合理路线是选择一个强基座，训练 MathMirror 所需的“通用教学行为”。

### 通用训练数据

需要跨五门课程共同收集：

1. 渐进提示数据；
2. 学生处于不同卡点时应给什么帮助；
3. 好提示与坏提示的偏好对；
4. Learning Evidence 抽取标注；
5. “证据不足时不要判断”的样例；
6. 根据学生历史改变提示的个性化样例；
7. 模型应该拒绝武断诊断的反例。

例如：

```json
{
  "student_context": {
    "known_stable": ["能够识别Rolle定理"],
    "possible_difficulty": ["辅助函数构造"]
  },
  "problem": "……",
  "request": "我不知道怎么开始",
  "target": {
    "hint_level": 1,
    "hint_type": "construction_goal",
    "response": "如果要使用Rolle定理，你希望辅助函数的两个端点满足什么关系？"
  }
}
```

训练方式可以依次是：

```text
Prompt + few-shot 基线
→ SFT 监督微调
→ 偏好优化
→ Eval 验证
```

但在积累足够数据前，先用 Prompt 和结构化输出做基线。不能为了比赛展示“我们微调过”而使用少量低质量合成数据训练。

## 三、如何得到每门 Course Mirror

### 第一步：建设课程数据，不训练

例如数分 Mirror：

先验证模型在检索教材和调用工具后是否已经足够好。

### 第三步：Eval 发现稳定缺陷后才训练

- 定理条件遗漏；
- 证明结构不完整；

## 六、OCR 应该怎样做

OCR 是数据入口，不等于训练模型。

```text
教材PDF / 拍题图片 / 手写作业
          ↓
图像裁剪、旋转、透视和去阴影
          ↓
版面分析
 ├─ 正文
 ├─ 数学公式
 ├─ 图片/坐标图
 ├─ 学生手写过程
 └─ 教师批注
          ↓
中文OCR + 公式OCR + 手写识别
          ↓
置信度标记
          ↓
人工校对
          ↓
结构化 CoursePack / Learning Event
```

不能把 OCR 结果未经校对直接当训练数据，尤其是数学公式。一个负号、上下标或量词识别错误就可能改变整道题。

OCR 输出应类似：

```json
{
  "image_id": "img_001",
  "regions": [
    {
      "type": "problem_text",
      "text": "设数列……",
      "bbox": [20, 40, 900, 460],
      "confidence": 0.97
    },
    {
      "type": "formula",
      "latex": "\\lim_{n\\to\\infty}a_n=A",
      "confidence": 0.82,
      "needs_review": true
    }
  ]
}
```

## 七、PostgreSQL 是做什么的

PostgreSQL 不负责训练模型，它负责可靠地保存和查询平台数据：

```text
用户和权限
课程与教材版本
知识节点和题目
CoursePack元数据
学习会话和事件
Learning Evidence
学生学习假设
作业Workspace
TA确认
Eval结果
版权和删除策略
```

教材 PDF、题目图片、手写作业放在 MinIO/S3；PostgreSQL 保存文件地址、结构化内容和关联关系。

pgvector 则保存文本的向量表示，用于：

```text
关键词检索
+
向量语义检索
+
课程/章节/版权过滤
```
